# Blender Bridge/Hub v1 Provider Runtime Design

## Purpose and milestone boundary

This milestone adds the local mixed-provider runtime that connects Blender Hub to operator-configured MCP providers on the same workstation. It initializes each provider independently, discovers its tools, registers provider-bound handlers in the accepted Task 1 `NamespacedToolCatalog`, and invokes every tool through `NamespacedToolCatalog.invoke`.

The Hub remains an upstream-first, transport-neutral multiplexer. It does not flatten the DCC gateway, port `fusion.cad/v1`, interpret CAD results, install providers, expose public Bridge MCP tools, use the VPS relay or `DesktopNodeService`, add a Windows GUI, implement Print Pipeline behavior, or perform live Blender/Orca calls. A local Hub MCP server is explicitly deferred because this milestone can prove discovery, supervision, namespacing, and invocation without adding an external surface.

## Components and ownership

The implementation is split to keep lifecycle, transport, and catalog policy small:

- `app.blender_hub.providers` owns validated provider configuration, transport-neutral session/result contracts, MCP model conversion, and the production Streamable HTTP and stdio connectors.
- `app.blender_hub.supervisor` owns configured provider instances, state transitions, explicit connect/refresh/close operations, DCC surface policy, and catalog registration.
- `app.blender_hub.catalog` remains the authority for namespace collision detection, availability checks, immutable mutation classification, and the one global mutation lock. It gains only the descriptor fields needed to retain upstream schemas and display metadata.

`agents/windows_fusion_agent.py` is a lifecycle donor only. It remains Fusion-specific and is not modified or generalized. `DesktopNodeService` is not used because its state, journal, messages, and mutation defaults are Fusion-named; relay generalization is a later milestone.

## Provider configuration

`ProviderConfig` has an operator-owned `provider_id`, `namespace`, and `kind`. `kind` is one of `dcc_gateway`, `three_mf`, `orca`, or `research`; only `dcc_gateway` changes publication policy. IDs and namespaces are ASCII, 1–64 characters, begin with an alphanumeric character, and thereafter contain only alphanumerics, `_`, or `-`. Namespace qualification remains the Task 1 behavior (`{namespace}.{upstream_name}`); dots are excluded from namespaces so the boundary is unambiguous. A supervisor configuration rejects duplicate provider IDs and duplicate namespaces before creating sessions or changing the catalog. Provider tool-name collisions remain `NamespacedToolCatalog` policy.

HTTP configuration contains one URL and optional per-call MCP `read_timeout_seconds`. `StreamableHttpProvider` accepts only `http` or `https` URLs whose parsed hostname is exactly `127.0.0.1`, `localhost` (case-insensitive), or `::1`. A port must be explicit and in 1–65535. User-info credentials, query strings, fragments, and empty/relative URLs are rejected. `HttpProviderConfig` and `StdioProviderConfig` are transport choices independent of `ProviderKind`; kind affects publication policy, not transport eligibility.

URL validation alone is insufficient because MCP SDK 2.0.0's `create_mcp_http_client()` defaults to `follow_redirects=True`. `StreamableHttpProvider` therefore creates and owns a dedicated `httpx2.AsyncClient`, enters it in the same `AsyncExitStack`, and passes it explicitly as `http_client=` to `streamable_http_client`. The client has `follow_redirects=False`, `trust_env=False`, and an explicit SDK-matching timeout profile: connect, write, and pool are 30 seconds and read is 300 seconds. It never uses the SDK-created default client, proxy/environment routing, or redirect following. Any 3xx response from the validated local MCP endpoint is a connection/protocol failure and is never followed. The transport HTTP timeout profile is distinct from the separately configurable MCP `read_timeout_seconds` applied to `call_tool`. The provider is not a general HTTP or SSRF facility and accepts no URL from tool arguments.

Stdio configuration contains an argv tuple, optional working directory, explicit environment overrides, and optional per-call MCP `read_timeout_seconds`. It is loaded only from operator configuration, never from MCP/model call arguments. The command and arguments are passed to `StdioServerParameters(command=argv[0], args=list(argv[1:]), env=..., cwd=...)`; no shell is involved. The runtime performs no package resolution, download, or install.

The stdio environment is a minimal platform-neutral merge: copy only present baseline keys from `PATH`, `PATHEXT`, `SYSTEMROOT`, `WINDIR`, `COMSPEC`, `TEMP`, `TMP`, `TMPDIR`, `LANG`, and `LC_ALL`, then apply operator overrides. An override may set or replace a value but cannot delete a baseline key. Environment keys must match `[A-Za-z_][A-Za-z0-9_]{0,63}`; there may be at most 128 overrides, each value is a string of at most 4096 characters, and the UTF-8 encoded merged `key=value` data is at most 16 KiB. Argv has 1–64 nonempty strings, each at most 4096 characters. These limits are validation boundaries, not secret classification. Public provider status and catalog tool metadata contain no argv, environment, URL user-info, or configuration dump; errors are reduced to exception type plus a bounded non-secret phase message. Tests use sentinel secrets to prove they are absent.

## Transport-neutral session and MCP connectors

The internal async `ProviderSession` protocol exposes exactly:

```python
async def initialize(self) -> None: ...
async def list_tools(self) -> tuple[UpstreamTool, ...]: ...
async def call_tool(self, name: str, arguments: dict[str, object]) -> object: ...
async def close(self) -> None: ...
```

`ProviderConnector.connect(config) -> ProviderSession` is injectable. Production HTTP and stdio implementations manually own one `AsyncExitStack`, enter the SDK transport context, enter `mcp.ClientSession`, and expose initialization/list/call through a small SDK session adapter. The HTTP implementation also enters its dedicated `httpx2.AsyncClient` before the transport context. `close()` closes the stack once and is safe after partial connection failure. There is no background retry task.

The adapter defines a narrow typed SDK boundary. `ProviderSessionFailure(provider_id, phase, exception_type)` is the base for failures raised by the concrete MCP SDK await or context operation itself; `ProviderConnectionError` represents connector/context-entry failures with `phase="connect"`. `_McpProviderSession.initialize`, `list_tools`, and `call_tool` wrap only `await session.initialize()`, `await session.list_tools()`, and `await session.call_tool()`, respectively. Each wrapper captures only provider ID, stable phase, and raw exception type, leaves the raw `except` block, and only then raises the sanitized typed failure. The public exception must have both `__cause__ is None` and `__context__ is None`; `raise ... from None` inside the raw handler is insufficient. `asyncio.CancelledError` propagates untouched.

Cleanup has one executable path. A private immutable `CleanupIssue(exception_type, phase)` contains no exception object or message. A helper performs exactly one `AsyncExitStack.aclose()`/session-close attempt. It catches ordinary `Exception`, including `ExceptionGroup`, inside the helper, immediately reduces it to `CleanupIssue`, drops the raw object, and returns; it never raises an ordinary cleanup error. It does not catch or suppress `asyncio.CancelledError`, so cancellation wins.

Connector entry owns the stack before entering any context. On a primary SDK/transport context-entry failure, a narrow raw handler records only exception type and stable entry phase and exits; the connector then calls the cleanup helper. The primary entry failure wins over an ordinary cleanup issue. From an outer point with no active exception, it raises sanitized `ProviderConnectionError` with `__cause__` and `__context__` both `None`; at most sanitized cleanup type/phase metadata may accompany it. On setup cancellation, the connector retains only cancellation intent, attempts cleanup once, and propagates cancellation; cancellation raised by cleanup propagates immediately. `_McpProviderSession.close()` uses the same helper: an ordinary cleanup issue becomes sanitized unchained `ProviderSessionFailure(phase="close")` only after the helper returns, while cancellation remains untouched. Supervisor best-effort close consumes only this sanitized close failure/metadata, and `close_all` continues siblings after it.

Conversion, `model_dump`, immutable snapshot construction, schema validation, policy/catalog decisions, and other programming errors occur outside those narrow handlers and are never reclassified as SDK/session failures. During ordinary calls/refresh they propagate without poisoning a usable session, subject only to the explicit quarantine rules below. During the destructive connect/reconnect transaction they trigger candidate cleanup and the local-abort state described below; the original non-SDK exception then propagates unchanged. No raw exception message or configuration is copied to public status or typed errors.

`UpstreamTool` is an immutable JSON-safe snapshot of the MCP `Tool`: name, title, description, `inputSchema`, optional `outputSchema`, annotations, and the remaining SDK-supported publication fields (`execution`, `icons`, and `_meta`) retained as upstream metadata. Conversion uses Pydantic JSON mode and aliases. In particular, annotations are mapped with `model_dump(mode="json", by_alias=True, exclude_none=True)` to the existing Task 1 `ProviderTool.metadata`, preserving exactly the canonical `readOnlyHint`, `destructiveHint`, `idempotentHint`, and `openWorldHint` values supplied upstream. The Hub neither supplies defaults nor derives hints from tool names or provider kind. The catalog snapshots the annotation mapping and schemas on registration so caller or SDK model mutation cannot change classification or publication evidence later.

`call_tool` returns the SDK result converted with `model_dump(mode="json", by_alias=True, exclude_none=True)`. This preserves MCP content, structured content, `isError`, result type, and result metadata as JSON-safe evidence. The Hub adds no CAD semantics and does not reinterpret an MCP `isError` result as a transport failure.

## Supervisor lifecycle and state machine

`ProviderSupervisor` receives a fully validated configuration collection, a connector selected per transport, and the Task 1 catalog. It owns one session, one monotonic integer `publication_generation`, the selected published-name snapshot, and one `asyncio.Lock` per provider. That single lock serializes every lifecycle operation and every upstream call for that provider, including read calls; this conservative v1 rule prevents call-versus-close/reconnect races without reference counting. Calls to different providers may overlap, subject to the catalog's existing global mutation lock.

At construction, every configured provider is registered with no tools and state `OFFLINE` with reason `not_connected`. The explicit lifecycle is:

```text
OFFLINE --connect succeeds and surface validates--> ONLINE
OFFLINE --connect/initialize/list failure---------> OFFLINE
ONLINE/DEGRADED --refresh succeeds----------------> ONLINE
ONLINE/DEGRADED --refresh incomplete DCC surface--> DEGRADED, session unusable
ONLINE/DEGRADED --refresh publication failure-----> DEGRADED, conditionally usable
ONLINE/DEGRADED --refresh SDK/session failure-----> DEGRADED, session unusable
ONLINE/DEGRADED --call SDK/session failure--------> DEGRADED, session unusable
any state --explicit close------------------------> OFFLINE
DEGRADED/OFFLINE --explicit connect/reconnect-----> ONLINE on success
```

`connect(provider_id)` and `reconnect(provider_id)` have identical destructive, one-attempt replacement semantics even when invoked while usable; callers must not expect rollback to the old session. Under the provider lock, the transaction first increments `publication_generation`, atomically registers an empty provider surface, detaches the old session, and marks the runtime unusable `OFFLINE` with a stable replacement-started reason. It then best-effort closes the old session. If close returns a sanitized close failure, the attempt stops conservatively with no second local provider session/process created; the runtime remains `session=None`, `OFFLINE`, and empty. If old-session close raises `asyncio.CancelledError`, cancellation propagates from this already-invalidated state and no candidate is created.

The candidate session is staged only in a local variable and is never installed into runtime during connector/context entry, initialize, SDK list, conversion/snapshot, surface selection/policy, handler construction, or catalog registration. From the instant a candidate `ProviderSession` exists until commit, exactly one local owner holds it. Every pre-commit exit transfers that candidate through exactly one cleanup attempt before leaving: typed and ordinary failures and `asyncio.CancelledError`/other cancellation raised during initialize, SDK list, conversion/snapshot, policy/selection, handler construction, or even a synchronous catalog test double. Candidate handlers close over the already-current empty generation token. Synchronous atomic `catalog.register_provider` and the subsequent installation of the runtime session, selected/published-name snapshot, status, and generation are one synchronous critical section under the provider lock with no `await` or cancellation point between registration return and completed commit. If synchronous registration raises `CancelledError` before returning, commit has not occurred and candidate cleanup applies.

For a primary candidate-stage cancellation, the supervisor retains only cancellation intent and a bounded stable `replacement_cancelled`/phase status value, never the exception object, message, or configuration; it makes exactly one candidate-close attempt through the existing cleanup contract. An ordinary sanitized `ProviderSessionFailure`/`CleanupIssue` from that close neither leaks a raw chain nor replaces the primary cancellation. If candidate close itself raises `asyncio.CancelledError`, cancellation wins immediately. Cancellation is propagated unchanged, never converted to `ProviderSessionFailure`, `ProviderConnectionError`, or `ProviderCallFailure`. A typed connection/SDK failure closes the candidate once if it exists and returns the existing sanitized one-attempt failure outcome. Incomplete DCC policy closes it and leaves `OFFLINE/canonical_surface_incomplete`. Any non-SDK conversion, schema, policy-implementation, handler/snapshot, catalog, or programming failure closes the candidate, records only a stable sanitized `OFFLINE` local-abort phase and exception type (never raw message/config), and propagates the original exception unchanged. Catalog atomicity means registration failure leaves the transaction's empty publication. Every pre-commit exit, including cancellation, leaves `session=None`, unusable, empty publication, and `OFFLINE`; the invalidated old session/publication is never resurrected. A later explicit reconnect may recover.

`refresh(provider_id)` runs under the same provider lock and uses the current usable session. If typed SDK `list_tools` failure occurs without a surface change, refresh atomically detaches the session (`session=None` and unusable), retains the catalog snapshot and generation as-is, marks the provider `DEGRADED`, and closes the detached session best-effort. Subsequent fresh invocation reaches the matching retained handler and fails fast with `ProviderSessionUnavailable` without touching upstream.

Every surface-change quarantine that intentionally keeps last-known tools visible—at minimum incomplete DCC refresh and publication failure where any previously published upstream name is missing—republishes retained evidence under a new generation while holding the provider lock. The supervisor chooses the next `publication_generation`, rebuilds the retained snapshot from the exact already-accepted immutable names, schemas, display/publication metadata, and `ToolAnnotations`, changing only handlers so they close over the chosen generation, and synchronously atomically calls `catalog.register_provider`. It does not rediscover or synthesize annotations or schemas. For incomplete DCC discovery, extra aliases remain ignored and no partial new canonical surface is published. Only after retained registration succeeds does it commit runtime generation; it then detaches/quarantines the current session, marks `DEGRADED` unusable, and best-effort closes the session. Thus a pre-quarantine captured read or mutating handler fails first with sanitized unchained `ProviderToolStale`, while a fresh lookup receives the republished matching-generation handler and fails with sanitized unchained `ProviderSessionUnavailable`; both make zero upstream calls. A small pure helper compares prior and selected name sets for the publication-failure decision; this is not a general policy-error or surface-diff mechanism. A later successful refresh replaces the snapshot and restores `ONLINE`; after quarantine, explicit connect/reconnect is required.

Although the retained evidence is already accepted, retained-snapshot registration can still expose a catalog programming/collision failure. If that atomic republish fails, the supervisor must not leave the old-generation visible snapshot. Under the same provider lock it atomically registers an empty provider surface, advances runtime `publication_generation` to the already chosen next generation, detaches/quarantines the session, and records `DEGRADED` unusable with only a stable sanitized internal publication-abort reason and exception type. It then best-effort closes the session and propagates the original non-SDK catalog/programming exception unchanged. No raw error message or configuration reaches status. Already captured old handlers are stale by generation and fresh lookup finds no tool. The empty registration and simple single-step generation advance preserve monotonic semantics.

`close(provider_id)` atomically detaches its session under the provider lock, clears only that provider's published tools, marks it `OFFLINE`, and closes the detached session best-effort. A sanitized close error cannot reverse detachment or publication clearing. `close_all()` performs that operation independently per provider; one close error cannot prevent other providers from closing. There is no timer, watchdog, exponential backoff, or automatic reconnect in this milestone. The operator/runtime owner explicitly calls connect, refresh, or reconnect, and each method performs one bounded attempt.

Every lifecycle path that clears publication—including connect/reconnect pre-invalidation, close, failed-reconnect clearing, and retained-republish abort—increments `publication_generation` before or with synchronous atomic empty registration. A surface-change quarantine that intentionally retains an old visible snapshot atomically republishes the exact retained evidence with new-generation handlers before committing that generation, so captured old handlers cannot masquerade as current. A pure SDK refresh/session failure with unchanged retained publication may leave the generation unchanged; unusability still makes fresh handlers fail with `ProviderSessionUnavailable`.

Catalog registration and status mutation occur in the provider operation's per-provider lock. `NamespacedToolCatalog.register_provider` continues to validate a proposed replacement before changing entries. For successful refresh replacement, the supervisor chooses the next generation, constructs all handlers with it, and calls synchronous atomic registration while holding the lock; only after registration succeeds does it commit runtime generation and the selected published-name snapshot. Registration return and runtime commit form one synchronous, await-free critical section. Queued handlers cannot enter the provider lock during this sequence, and newly registered handlers therefore cannot observe a pre-commit generation after release. If new-surface registration fails, generation and the old authoritative publication initially remain unchanged while the usability/quarantine helper decides the outcome: an unchanged/prior-name-complete surface may remain usable, whereas a missing-prior-name outcome performs the retained-snapshot new-generation republish described above. Failure of that retained republish clears publication and advances generation; it never leaves an old-generation visible snapshot.

Lock ordering is fixed: a catalog invocation requiring mutation serialization acquires the catalog global mutation lock before its provider handler acquires the provider lock. Lifecycle paths acquire only the provider lock and must never call `catalog.invoke` while holding it. Synchronous `register_provider` and `set_provider_status` do not acquire the global mutation lock. No path may acquire the global mutation lock while already holding a provider lock.

## DCC gateway surface

For `kind=dcc_gateway`, the only publishable upstream names are exactly `search`, `describe`, `load_skill`, and `call`. A complete canonical set is required. Compatibility aliases or any additional upstream tools returned by `list_tools` are ignored and are never registered by the Hub.

If any canonical tool is missing, connection is considered policy-incomplete: on first connect/reconnect the session is closed, no DCC tools are published, and the provider is `OFFLINE` with a bounded `canonical_surface_incomplete` error. During refresh, the prior complete four-tool evidence may remain visible for inspection only after it is atomically republished with next-generation handlers as specified above; the current session is then quarantined/detached and best-effort closed, and the provider becomes `DEGRADED` and unusable with that error. A captured pre-quarantine handler is stale, while a fresh retained handler fails fast with `ProviderSessionUnavailable` until explicit connect/reconnect. No partial canonical surface is published or invoked. Stdio 3MF, Orca, and research providers publish their complete listed surfaces under their configured namespaces, subject to catalog collision checks.

## Invocation and failure semantics

For each accepted tool, the supervisor creates a handler closed over its provider ID, upstream tool name, and the exact `publication_generation` that created that publication. Public callers use `ProviderSupervisor.invoke(qualified_name, arguments)`, which delegates immediately to `NamespacedToolCatalog.invoke`; the handler never calls the catalog and no direct provider-call API is public. Consequently every unknown or mutating tool still passes through the one Task 1 global mutation lock across all providers.

The handler enters its provider lock and, before checking or using a session/upstream, compares its captured generation with the runtime generation. A mismatch raises sanitized unchained `ProviderToolStale(provider_id, tool_name)` with zero upstream access; it neither degrades the provider nor retries. On a match it verifies that a current usable session exists and uses that exact session for the entire upstream call. It never redirects an in-flight call to a replacement. Last-known tool metadata remains published while `DEGRADED`, but if the session has been detached a later invocation raises typed `ProviderSessionUnavailable(provider_id, tool_name)` before any upstream access. These handler-level errors are sanitized and affect no other provider.

Arguments must be a JSON-object-shaped `dict[str, object]` and are forwarded unchanged. A normal MCP result is returned in its JSON-safe form. If the adapter raises typed `ProviderSessionFailure` during `call_tool`, the handler, while still holding the provider lock, atomically detaches that exact session (`session=None` and unusable), marks only the provider `DEGRADED`, then closes the detached session best-effort. After leaving the adapter-failure handler it raises `ProviderCallFailure(provider_id, tool_name, phase="call", exception_type=...)` without chaining the adapter failure. `ProviderSessionUnavailable` follows the same sanitized, unchained rule. These public errors contain only provider ID, phase, tool name where applicable, exception type, and bounded stable code/text—never raw `str(exc)`, URL, argv, cwd, environment, arguments, or result content—and both `__cause__` and `__context__` are `None`. The call count is exactly one: there is no replay or automatic reconnect, including for mutations. Task 1's `dispatch_with_replay_policy` is not used here; it is reserved for a later transport boundary that can prove call kind and reconnect semantics.

The supervisor catches only typed `ProviderSessionFailure` for SDK detach/degrade semantics; it never places adapter calls, conversion, policy, catalog, or arbitrary programming logic under a broad handler that reclassifies them. The adapter distinguishes MCP protocol results (including `isError`) from exceptions. During ordinary invocation/refresh, conversion/policy/programming exceptions propagate and do not detach or poison a usable session, except for the explicit DCC incompleteness and prior-name publication quarantine decisions above; connect/reconnect instead follows its deliberately destructive local-abort transaction. `asyncio.CancelledError` always propagates and does not by itself mark a healthy provider degraded or detach its session; destructive connect/reconnect is intentionally different because invalidation already occurred and every owned pre-commit candidate must be cleaned exactly once before cancellation leaves. Transaction invalidation or cleanup already performed before cancellation is not rolled back. Because call, close, refresh, connect, and reconnect share one provider lock, a lifecycle operation racing a call begins only after that call finishes, and an already-started call cannot be redirected to a stale or new session.

## Verification strategy

Unit tests use fake `ProviderSession` and connector implementations. They prove validation boundaries, state transitions, provider isolation, atomic refresh, DCC filtering/incompleteness and quarantine, exact schema/annotation/result preservation, global mutation serialization and lock order, per-provider call/lifecycle serialization, cancellation propagation, fail-fast unusable sessions, and no replay after failures. Deterministic read and mutation tests capture an old handler before incomplete-DCC and missing-prior-name quarantine, republish the exact retained snapshot at the next generation, and prove the old handler raises `ProviderToolStale` with zero upstream calls while fresh lookup of the same retained tool raises `ProviderSessionUnavailable` with zero upstream calls; retained names, schemas, display/publication metadata, and annotations remain unchanged. A retained-republish-failure test proves publication clearing, generation advance, `DEGRADED` unusable/session-none state, propagation of the original non-SDK exception, no raw status leakage, stale captured handlers, and absent fresh lookup. Successful refresh tests retain commit-after-registration semantics.

Candidate-transaction tests inject cancellation during candidate initialize, SDK list, conversion/snapshot, policy/selection, handler construction, and a synchronous catalog-registration fake. For both connect and reconnect they assert empty publication, `session=None`/unusable `OFFLINE`, exactly one candidate-close attempt, no old resurrection, unchanged cancellation propagation, and no secret leakage. Separate cases combine primary cancellation with ordinary sanitized close failure, make candidate close itself raise `CancelledError`, and cancel old-session close before candidate creation; cancellation wins as specified, and the old-close case creates no candidate. Typed and ordinary candidate-stage failures retain the same exactly-once ownership assertions and later explicit recovery.

Cleanup tests combine a secret-bearing primary entry failure with a different secret-bearing cleanup failure/`ExceptionGroup`. They assert primary exception-type precedence, absence of both sentinels from `str`, `repr`, status, formatted traceback, recursive cause/context and nested exception-group traversal, and `None` public wrapper cause/context. Cleanup-only close failure and cleanup cancellation tests prove sanitized close behavior and cancellation precedence. Exact boundary tests retain the distinction between SDK failures and non-SDK conversion/policy/catalog/programming exceptions. No unit test opens a socket, resolves a host, launches a subprocess, downloads a package, or invokes Blender/Orca.

Narrow connector tests monkeypatch `httpx2.AsyncClient`, `streamable_http_client`, `stdio_client`, and `ClientSession` async context managers. They prove the explicitly supplied HTTP client has `follow_redirects=False`, `trust_env=False`, 30-second connect/write/pool timeouts and a 300-second read timeout, and that no SDK default-client path is used. They also assert the validated URL, exact command/args, minimal merged environment, initialize/list/call ordering, JSON-mode conversion, and close behavior. The tests remain network-free and run on Windows and Linux without signals, process groups, `/proc`, Unix sockets, or shell assumptions.
